## 결제와 현금영수증

| 조건 | 원문 기준 |
|---|---|
| 현금·계좌이체·무통장 | 현금영수증 대상. 거래월 다음 달 10일까지 요청한다. 이후 조합 발행은 불가하며 국세청 자율 발급 절차를 안내한다. (§1~2) |
| 카드 | 카드 매출전표를 사용하며 별도 발행을 중복 증빙으로 보아 하지 않는다. (§1) |
| 적립금·쿠폰 | 사용·차감분은 증빙 발행 대상이 아니다. 정가가 아닌 실제 받은 금액을 기준으로 한다. (§1) |
| 분할결제 | 수단별로 나눠 현금분만 현금영수증, 카드분은 매출전표로 처리한다. (§1) |
| 유형·번호 | 고객에게 소득공제/지출증빙 유형을 확인한다. 휴대폰번호·현금영수증카드·사업자등록번호 중 지정번호를 받는다. 개인도 지출증빙용을 요청할 수 있으나 사업자의 소득공제용 요청은 불가하다. (§2) |
| 개인정보 | 고객이 번호를 제시하기 전에 기존 등록번호를 상담사가 먼저 읽어 주지 않는다. (§2) |

§2의 개인 지출증빙 요청 가능은 현금영수증의 **유형**에 관한 규칙이다. §3·§6의 실제 결제·공급받은 사업자의 **세금계산서 명의** 제한과 구분한다. 거래월 다음 달 10일의 구체적인 시간·휴일 연장 규칙은 원문에서 확인되지 않았다.

## 사업자 세금계산서와 정정

- 도매 사업자 거래는 별도의 도매 거래 조건을 따른다. 세금계산서는 실제 결제하고 공급받은 사업자 명의로 발행하며, 사업자등록증과 결제 명의를 대조한다. 상호, 사업자등록번호, 대표자명, 업태·종목, 수취 이메일을 확인한다. 월 마감분 익월 10일까지 건별 또는 정기 공급 거래처의 월 합계 발행이다. 정정·재발행에는 1~2영업일이 걸린다. (§1·§3)
- 미가공 농·수산물 상품분은 면세로 세액이 0원이거나 공란이다. 배송·운송 등 용역분을 함께 청구하면 상품분과 분리하고 해당 용역분만 과세한다. 모든 청구 금액을 일괄 면세로 처리하지 않는다. (§3)
- 실제 결제자와 다른 사업자 명의, 허위 사업자, 개인 결제분의 사업자 명의, 실결제액 초과, 허위 품목·품명, 기한 지난 소급 발행 및 취소 거래의 증빙 유지 요청은 거절 사유를 설명한다. (§6)
- 명의 오류 TX-05는 정정이 아닌 **기존 증빙 취소 후 정당 명의 재발행**이다. 거절 대상에 먼저 발행한 다음 정정해 우회하는 방법은 금지한다. 기재 오류 TX-01은 수정, 중복 TX-04는 후행분 취소, 필요 기재사항 누락 TX-06은 재발행이다. (§4)
- 카드의 별도 증빙 제한과 도매 전자세금계산서 기준의 적용 관계, 특히 카드로 결제한 사업자 도매 거래에서 전자세금계산서가 허용되는지는 §1·§3만으로 확정하지 않는다.

## 환불 시 증빙

| 상황 | 처리 |
|---|---|
| 발행 전 환불 | 발행하지 않는다. 원문은 이 행에서 부분환불 여부를 구분하지 않으므로 발행 전 부분환불의 잔액 발행 방식은 추가 확인한다. (§5) |
| 전액환불 | 현금영수증 취소 / 세금계산서 TX-03 전액 취소 발행. (§4~5) |
| 부분환불 | 원본을 취소하지 않고 차액만큼 TX-02 수정 발행; 재차 부분환불하면 잔액 기준으로 다시 수정한다. (§4~5) |
| 발행월 마감 후 | 취소·수정 발행일은 환불 승인일 기준. (§5) |
| 적립금 환불 | 현금 환급이 아니므로 증빙 정정 없음. (§5) |

이 문서는 **확정된 환불액의 증빙 반영**을 다루며, 환불 인정 여부나 비율 자체는 [부분환불 산식](partial_refund_evidence.md)을 별도로 확인한다. (§5)

## 공개 L-05와 API 연결 검토

[공개 L-05](public_tc_matrix.md)는 무통장 주문과 발행 구분을 확인하고 API 07로 주문·결제를 확인한 뒤 API 32로 지정번호 접수를 요구한다. 대화에서는 확인된 거래가 현금영수증 대상인지, 실결제액·거래월과 기한, 고객이 원하는 유형 및 고객이 제시한 지정번호를 먼저 확인해야 한다. 주문 데이터에 필요 필드가 실제로 포함되는지와 최신 결제 상태는 아직 API 원문 및 실행 결과로 확인되지 않았다.

현재 [로컬 API 어댑터](../action_api.py)는 `ApprovedCashReceipt`에 `approval_no`와 `receipt_number`를 받고, API 32에 결제 승인번호를 경로로, `receipt_number`를 본문으로 전달한다. 성공 응답은 요청 ID·대상 승인번호·`request_status=SUBMITTED`·요청 시각을 검증한다. 이 **SUBMITTED는 접수**이며 세무 증빙의 발행 완료를 확인한 것이 아니다. 원문 §7의 홈택스 통상 다음 영업일 조회 안내는 발행이 완료된 경우에만 적용한다. [API 공통 규약](action_api_basics.md)에 따르면 같은 대상 재접수는 기존 번호를 유지하면서 마지막 본문으로 갱신될 수 있으므로, 접수 상태가 불명확한 경우 결과와 본문을 확인해야 한다.

현재 어댑터에는 소득공제/지출증빙 유형 필드가 보이지 않는다. 개인이 지출증빙을 선택할 수 있으므로 번호만 보고 유형을 추정하거나 요청에 반영되었다고 말할 수 없다. **실제 API 32가 별도 유형 필드를 지원하는지, `receipt_number`의 지정번호 종류별 처리와 필수 형식, 분할결제 처리 및 발행 완료 확인 경로는 미확인**이다. 로컬 어댑터에서 보이지 않는다는 사실만으로 공식 API에 필드가 없다고 단정하지 않는다. 세금계산서 신규·취소·수정 발행을 연결할 API와 필수 필드 역시 확인되지 않았다. 이 분석에서는 API를 호출하지 않았다.
