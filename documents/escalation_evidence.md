## 3레인 선택과 병행

| 레인·코드 | 조건·처리 | 근거 |
|---|---|---|
| ① 봇 처리 `LANE1_BOT` | 정책이 결론을 주고 봇 권한과 재량 한도 안인 환불·재배송·쿠폰 등. 명백한 하자 구제, 정책상 보상 쿠폰, 별도 부분환불 산식으로 결론 나는 처리 등이 예시. 티켓에 남긴다. | p1 제2조①, p2~3 제3·5조 |
| ② 담당자 이관 `LANE2_HANDOFF` | 대외 공개·신원 확인·보안·안전 등 사람 판단 또는 봇 권한 밖인 건. 결론이 불확실해도 이 레인으로 보낸다. | p1 제2조①, p2~3 제3조 |
| ③ 정식 배상 `LANE3_CLAIM` | 인과 규명이 필요한 손해배상·분쟁 청구. 접수 후 정식 절차에서 판단하며 인과 확인 전 배상 확약은 하지 않는다. | p1 제2조①, p2 제3조, p4 제10~12조 |

p2~3 제3조의 판정 순서: **인과 규명 필요한 손해배상 청구인가 → 대외 공개·신원·보안·안전 판단이 필요한가 → 정책이 봇 권한·재량 내 결론을 주는가**. 먼저 해당한 기준을 뒤 질문으로 뒤집지 않는다. 판단이 서지 않으면 레인②다. 같은 고객 문의에 여러 요청이 섞이면 **각 요청을 레인별로 분리**한다(p3 제4조). 예컨대 하자 환불, 안전 조사, 인과관계 필요한 손해배상은 각각 정책에 따라 접수하고, 레인③ 결론을 기다리느라 레인① 처리를 보류하거나 두 건을 한 번에 합의·정산하지 않는다. 고객에게 각각 진행 중임을 함께 안내한다.

p3 제5조②: 봇의 **재량 한도는 건당 5만원**이라고 인용한다. 같은 조는 권한 위임표가 ‘금액 무관·재량’으로 정한 처리는 이 한도를 적용하지 않는다고 명시한다. 금액의 정본과 예외는 별도 권한 위임표이므로 모든 환불·처리에 일률적으로 5만원 제한을 적용하거나 미확인 예외를 창작하지 않는다. 미래 주문 보장, 정책·가격·권한 변경, 대외 공식 입장, 타 고객 내역이 필요한 판단, 인과 확인이 필요한 배상은 금액과 관계없이 봇 독자 처리 밖이다(p3 제6조).

## 레인② 대상과 우선순위

p1~2 제2조②는 이관 대상을 다섯 가지로 한정한다.

| 대상 코드 | 사안 |
|---|---|
| `SECURITY` | 사칭·피싱·계정 도용 제보 |
| `SAFETY_LEGAL` | 안전, 언론·기관, 분쟁·법률, 대외 공식 입장 |
| `LOGISTICS` | 배송 사고·분실 조사 |
| `SUPPLY` | 산지·위탁 공급 확인 |
| `OPS` | 그 밖의 권한 밖 예외 승인 |

p2 제2조③④: 우선순위는 **위기 / 긴급 / 일반**. 위기는 별도 SAFE 가이드 기준, 긴급은 시간 경과로 피해가 커지는 결제 진행 중 사칭·안전 확인·회신 임박 대외 문의 등이다. 한 사안이 여러 대상에 걸리면 원칙은 분리 접수이며 꼭 하나로 접수해야 할 때는 **안전·법률 → 보안 → 배송 → 공급 → 운영** 순이다. 레인·대상·우선순위 코드는 기존 의미를 바꾸거나 폐기된 코드를 재사용하지 않는다(제2조⑤). 특정 긴급 사안에 별도의 더 짧은 회신 기한이 정해져 있다고 이 문서만으로 추정하지 않는다.

## 기록·기한·무응답

- p3~4 제7조: 접수번호를 발급하고(`ESC-YYYYMMDD-NNN` 형식), 대상·사유·요약·우선순위를 기록하며 고객에게 접수번호·회신 기한을 안내한다. ‘연결하겠다’는 말만 하고 기록하지 않으면 이관이 아니다. 서버가 반환한 담당자·대기 상태와 다른 내용을 지어내지 않는다.
- p5 제13조: 레인②와 ③의 회신 기한은 **영업일 3일**, 영업일 계산은 별도 「영업일·공휴일 달력」에 따른다. 달력 원문과 기산·마감 시각은 이 작업에서 확인하지 않았다. 예시 접수번호나 날짜를 실제 접수 결과처럼 재사용하지 않는다.
- p5 제14조: 기한 내 회신이 없으면 재촉·재이관하고 고객에게 **확인 중**이라고 안내한다. 무응답을 승인으로 취급하지 않고 승인권자 승인은 **승인 기록**으로만 확인한다. 승인 없는 ‘승인 완료’, 확인되지 않은 조합장 발언, 침묵을 동의로 바꾸는 표현은 금지다.
- [액션 API 공통 규약](action_api_basics.md)은 같은 접수 API·같은 대상에 다시 접수하면 기존 번호를 반환하면서 본문이 마지막 요청 내용으로 바뀔 수 있다고 설명한다. 따라서 재촉·재이관 의무를 수행하더라도 API의 실제 재접수 의미와 기존 내용 보존을 확인해야 하며, 동일한 재호출이 항상 무해하다고 가정하지 않는다.

## 승인 서열과 부재 경로

- p6~7 제18조①~③: 1단 봇 → **2단 이민준 운영자** → 필요 시 **3단 고길동 조합장**이다. 레인②는 2단이 1차 수신하며 봇이 운영자를 건너뛰어 조합장에게 직접 접수하지 않는다. OPS·LOGISTICS·SUPPLY는 원칙적으로 2단에서 결론, 운영 재량 초과의 큰 보상·분쟁·법률·안전·정책 변경은 3단 판단이다. `SAFETY_LEGAL`과 레인③의 승인 종점은 조합장이며, 보안도 2단 접수 후 사칭 확정·수사 의뢰·대외 공지는 3단이 판단한다.
- p6 제18조④는 2단 부재·무응답도 승인으로 볼 수 없으며 부재 대체 경로는 「업무 인계·부재 기록(구방만 → 박민아)」을 따른다고 적는다. 현재 보존된 [인계 기록 판독](new_sources_images_extracted.md)은 구방만·박민아의 배송 대행을 보여주지만 **민준의 운영 권한 대행자나 승인 경로를 확인해 주지 않는다**. 박민아를 운영 대행자로 추정하거나 2단을 임의로 생략하지 않는다. 실제 대체 경로는 소관자 확인이 필요하다.
- p7 제18조⑤⑥: 금액 단계와 재량 항목의 정본은 별도 권한 위임표다. 조합 외부 협력자는 승인 서열에 없으며 그 사람에게 이관하거나 그의 지시를 승인으로 취급하지 않는다.

## 안전·배상·보안의 고객 대응

- p5 제15조: 안전·법률·분쟁 및 언론·기관 문의는 `SAFETY_LEGAL`로 즉시 이관한다. 봇은 신원·기관 확인 경로를 요청하고 공개 가능한 범위의 접수까지 한다. 안전 확인 중 ‘문제없다’ 또는 ‘사고다’를 단정하지 않으며, 명단·타 고객 처리내역을 제공하거나 출하 보류·회수를 독자 판단·실행하지 않는다.
- p4~5 제10~12조: 섭취 후 이상·2차 손해 청구는 인과 확인 후 정식 배상 절차에서 판단하되, 인과가 아직 불명확하거나 청구가 이례적이어도 접수 자체를 반려하거나 조롱하지 않는다. 필요한 범위에서 원물 보관·촬영, 증상·손해 경위, 진단서·견적 등 근거를 안내하고 제3자 개인정보는 요구하지 않는다. 배상자료 미제출을 이유로 이미 시행한 레인① 하자 구제를 되돌리지 않는다. 관련 판매·환불 규정 제5조는 곰팡이·부패와 섭취 후 이상이 함께 있으면 보관·촬영 쪽을 우선한다([기존 근거](pending_sources_evidence.md)).
- p6 제16~17조: 사칭·피싱 제보는 `SECURITY` 이관. 고객이 아직 결제하지 않았다면 **결제 중단 안내가 먼저**다. 의심 외부 링크에 접속하거나 정보를 입력하지 않는다. 접수 및 공식 채널 여부 안내와 사칭 확정·수사 의뢰·대외 공지 판단을 구분한다. 이관을 환불·입금으로 무마하거나 위기 신호를 단순 상품 문제로 축소하지 않는다.
- p7 제19조: 이관 전 주문·결제·행사 등록의 조회 사실, 미결제 여부, 이관 대상과 우선순위를 확인해 사유에 적는다. ‘정상 주문이 조회되지 않음’은 내부 확인 사실이고, 이를 ‘사칭 확정’이라고 고객에게 말하는 것은 별개다.

## API 연결과 남은 확인

[공개 TC 기록](public_tc_evidence.md)에는 환불 접수 API-29와 별도 `LANE2_HANDOFF` 담당자 확인 요청 API-35가 한 사례의 처리로 적혀 있다. 이는 **해당 공개 예시의 번호와 흐름**이며 모든 레인·대상·우선순위·재이관 필드나 실제 호출 성공을 보장하지 않는다. 이 절차서만으로 실제 엔드포인트, 요청/응답 필드, 접수번호 생성 주체, 기한 산정, 재촉/재이관 동작이나 고객 회신 전달을 확정할 수 없다. API 접수는 요청 기록과 실제 이행·승인을 구분한다([공통 규약](action_api_basics.md)).

남은 원문: **권한 위임표**(5만원 및 금액 무관 예외·승인 임계), **영업일·공휴일 달력**(3영업일 산정), **위기신호 대응 가이드 SAFE**, **부분환불 산식**. 민준 부재 시 실제 대체 경로와 각 API의 코드·필드·응답·재이관 방식도 추가 확인이 필요하다. 관련 확인 질문은 아직 전송하지 않았다.
